# Paper Ideation

Produce a topic the user can actually finish: academically publishable, built on data that can really be downloaded, and feasible for one researcher. Institutional or job relevance is a secondary criterion, never the first.

Apply the repository's [working principles](../../PRINCIPLES.md) throughout.

## Workflow

1. Collect the constraints before proposing anything: field, the user's existing expertise and models, journal rules (only SCI, SCIE or SSCI journals count; mega open-access venues do not), any institutional brief, and what the user can run themselves.
2. Propose five to eight candidates. For each give, in this order: research question, academic contribution (a method or a generalisable conclusion, not a report), data sources with URL and access mode (public download, API, restricted, non-existent), feasibility for one researcher with public data, and institutional relevance last.
3. Verify data access by visiting the portals, not by assumption. Record which sites the working environment cannot reach and what the user would have to download by hand. A candidate whose core data is private or unconfirmed is ranked down or dropped.
4. Rank by (a) academic contribution, (b) downloadable data, (c) realistic scope. Then run a counter-argument pass on the top candidates: what a reviewer would object to, which published papers are closest, whether a competing preprint already exists.
5. For the preferred candidate, build a prior-work table of about fifteen to twenty verified journal papers (DOI checked, abstract level) that states the gap concretely: the nearest papers and how their question differs, and papers that use the same data. This table is not the literature review; the full review of about one hundred papers comes later.
6. Deliver a document with a plain-language framing paragraph first (what the paper is, what it is not, how it links to the user's field or brief), the ranked candidates with evidence, and the explicit decisions the user must make. Ask for confirmation with one-word answers and a recommended option.
7. After confirmation, record the topic, the ranking criteria the user stated, the data plan and the next step in project memory, so later stages do not re-ask.

## Boundary

Ideation ends when the user has confirmed one topic, its research question and its data plan. Do not write a research design, collect data or draft text in this stage. A fast move from topic to design and draft was the main failure in practice; the literature review (paper-literature-review) must come before the design is frozen.
