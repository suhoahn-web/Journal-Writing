# Candidate evaluation

Each candidate is a row with the same fields, so the user can compare them.

| Field | What to write |
|---|---|
| Research question | One sentence, with the unit of analysis and the outcome |
| Academic contribution | Method, measurement or generalisable conclusion; say why a reviewer would care |
| Data | Every dataset: name, provider, URL, period, granularity, format, access mode |
| Access check | Visited on this date; downloadable without login / login needed / blocked from this environment / not public |
| Feasibility | Can one researcher finish it with public data and the user's own models; what must be assumed (for example a flat load when firm-level demand is private) |
| Nearest papers | Two or three verified journal papers and how their question differs |
| Institutional relevance | Only after the above; never the ranking key |

Rules learned in practice:

- A candidate ranked first for institutional fit was rejected by the user; academic contribution and downloadable data came first. Order the fields that way.
- "No paper does X" is not evidence. Give the nearest papers and the exact difference, and count how many authors name the gap as future work once the review is done.
- Reuse of old data is not guaranteed; if the years do not match, the data must be downloaded again.
- Crossref lookups are rate-limited; check DOIs a few at a time and record the result.
- When the environment cannot reach a portal, say so and give the user the exact menu path, filters and file names to download.
